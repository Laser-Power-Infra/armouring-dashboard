# KGP 4 Cards Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Four dashboard tabs, one per KGP card, showing the issued cards in the approved layout from data loaded out of the Google Sheet.

**Architecture:** Every card issue is kept. A load command copies the sheet's five output tabs plus `Drum stock` into tables under one `card_issues` row that carries the version, revision number and dates; older issues stay. One data table per card (the labour card has a second one for spare men). Pure functions in `lib/cards/` turn those rows into each card's figures by the build spec's rules. Four server-rendered pages under `/cards` print the template's markup with the template's stylesheet.

**Tech Stack:** Next.js 16.4.6, React 19, Prisma 7 on Neon Postgres, googleapis, vitest 5. No new dependency.

**Spec:** `docs/superpowers/specs/2026-11-19-kgp-cards-design.md`. Rule book: `docs/KGP_4_Cards_Build_Spec.md` ("build spec"). Look: `templates/*.html`.

## Global Constraints

- Read `node_modules/next/dist/docs/` for any Next API before using it (AGENTS.md).
- Schema changes go through a migration file only. Never `prisma db push`.
- Read every tab by heading, never by column letter (build spec 1).
- The sheet is read only. Scope stays `spreadsheets.readonly`.
- Never write "free", "freed" or "idle" for labour. Write "the labour can be utilized for some other purposes" (build spec 2.2).
- Card colours and sizes are fixed: blue `#1c3a6b`, light blue `#dfe7f3`, orange `#c2410c`, border `#9aa7bd`, green `#2e7d32`, yellow `#fde047`, grey `#eceff3`; Roboto 400/700, body 9pt; A4 landscape, margins 9mm, bottom 12mm.
- Card pages are public, like the dashboard. No sign-in in this plan (owner, 19-Nov-26).
- Every issue is kept. A load never deletes another issue's rows. Loading a version that is already stored replaces only that issue's rows.
- Version box text: `VERSION DD-Mon-YY / Rev n` from `card_issues`.
- Day 0 (D0) = earliest date in that issue's `card_plan` rows, stored as `card_issues.d0`. WIN = 15 for Cards 1, 3, 4; 14 for Card 2.
- No Claude or model attribution in commits or files. Commit only when tests, `npx tsc --noEmit` and `npx eslint app components lib tests scripts auth.ts proxy.ts` pass.
- Tests that touch a database use `TEST_DATABASE_URL` only and follow the guard at the top of `tests/db/views.test.ts`.
- The app database (`DATABASE_URL`) is written only in Task 6, after the owner says yes.

## Review Focus

- A tab arrives with an extra column or columns in another order: figures must not change (covered in Task 1).
- A date cell arrives as a serial number instead of text like `17-Nov-26`: must parse to the same day (Task 1).
- No issue is stored yet: each page shows "No cards have been issued yet", not an error (Task 3).
- A drum size the code has never seen, or `SIZE TO CONFIRM`: shown as "Size not known" and counted as held up, never dropped (Task 5).
- A machine in the tab that is not in the fixed list of 17: load fails with a message naming it, rather than the row vanishing from the card (Task 1).

**Interfaces:**
- Produces:
  - `MACHINE_ORDER: readonly string[]` = `WD14, WD17, Skip (12+7)-1, Skip (12+7)-2, Skip 8, Skip 10, Skip 11, MS-14, MS-11, MS-18, Laying 5, Armouring 5, Extruder 22, Extruder 35, Extruder 51, Extruder 52, Sioplas 4`

  - `parseCardPlan(values: unknown[][]): PlanRow[]`, `parseLabour`, `parseSpareMen`, `parseDrumNeed`, `parseDrumAssembly`, `parseDrumStock`
  - `sizeKey(s: string): string` (lower case, `×` to `x`, drop spaces and `-`), so `84 X 35 X 38 X 3 + EXTRA SEGMENT` and `84×35×38×3 + extra segment` give the same key
  - `parseVersion(text: string, d0: string): { issueDate: string; rev: number | null }` (`17-Nov R2 plan` with D0 2026-11-17 gives 2026-11-17 and 2; `VERSION 20-Nov-26 / Rev 6` gives 2026-11-20 and 6; no Rev in the text gives null)
  - `loadCards(db, tabs): Promise<{ issueId: number; version: string; rev: number; rows: Record<string, number> }>` where `tabs` is the seven value grids; `readCardTabs(spreadsheetId)` fetches them
  - Row types, one per table:

| Table | Card | Columns |
|---|---|---|
| `card_issues` | all | `id` serial, `version` text unique (as written in the sheet), `issue_date` date, `rev` int, `d0` date, `generated_at` timestamptz null (the "updated" time in the sheet's title, when readable), `loaded_at` timestamptz; unique (`issue_date`, `rev`) |
| `card_plan` | 1 | `id` serial, `issue_id`, `row_no`, `day` date, `process`, `machine`, `prod_order`, `mc`, `party_cable`, `lot`, `qty` float, `unit`, `size_core`, `material`, `feed`, `feed_status` (CHECK ok, drum, wait), `job` |
| `card_labour` | 2 | `id`, `issue_id`, `row_no`, `day`, `shift` (CHECK Day, Night), `machine`, `operator` null, `helpers` text[], `men_needed` int, `men_given` int, `note` null |
| `card_spare_men` | 2 | `issue_id`, `day`, `shift`, `men` text[]; key (`issue_id`, `day`, `shift`) |
| `card_drum_need` | 3 | `id`, `issue_id`, `row_no`, `used_on` date, `ready_by` date, `late` bool, `drum_size`, `drums_needed` int, `from_stock` int, `to_assemble` int, `prod_order`, `party_cable`, `lot`, `note` null |
| `card_drum_assembly` | 4 | `id`, `issue_id`, `row_no`, `assemble_by` date, `was` date null, `drum_size`, `drums` int, `flanges_needed` int, `flanges_from`, `prod_order`, `party_cable`, `lot`, `used_on` date |
| `card_drum_stock` | 3, 4 | `issue_id`, `size_key`, `drum_size`, `drums` int null, `flanges_kgp` int null, `flanges_pp` int null; key (`issue_id`, `size_key`). Stock as it was at that issue, so an old card keeps its figures |

`issue_id` references `card_issues(id)` with ON DELETE CASCADE and is indexed in every data table. `row_no` keeps the tab's row order, which is the plan order the cards print in. The Version column must hold one value across all five tabs; the load refuses mixed versions and names them.

Revision number: taken from the version text. When the text has none, it is the next number after the highest stored for that issue date.
